## 一、怎么量的（**别人可以照着复现**）

- **环境**：`uvicorn app.main:app`（同源部署，`frontend/dist` 已 `bun run build`）+ 无头 Chrome，
  `Emulation.setDeviceMetricsOverride(390×844, dsf=2, mobile=true)`。
- **坐标口径**：一律 `getBoundingClientRect()`；"溢出"分三档，**绝不混成一句"有溢出"**：
  1. **文档级**：`document.scrollingElement.scrollWidth − clientWidth`（真出现横向滚动条）；
  2. **被裁**：元素右边界超出**最近的 `overflow-x` 非 `visible` 祖先**的右边界 → 用户看不到；
  3. **自家可横滚**：元素自己 `overflow-x: auto|scroll` 且 `scrollWidth > clientWidth` → **这是有意的，不算 bug**。
- ⚠️ **为什么必须分这三档**：本项目 `.dw-layout` 是 `overflow: hidden`，
  所以"内容被顶到 904.9px"时**文档宽度仍是 390**——`scrollWidth` 一点异常都没有，
  vitest / build / 肉眼扫一眼都发现不了；只有第 2 档能量出"有东西被裁掉了"。
- 覆盖六屏：库 `/`、起草 `/write`、记忆 `/memory`、处理过程 `/process`、我的 `/me`、阅读 `/read/46`。
- 每屏都另取 2× PNG 截图，并与量出的数字**相互印证**（截图看"像不像坏的"，数字看"坏在哪一环"）。

## 二、量出来的四条

| # | 症状 | 量出来的数 | 根因 |
|---|---|---|---|
| ① | **阅读页目录展开后整屏被撑宽、右边全被裁掉** | `.mobile-reader` = **904.9px**（视口 390）、目录 = **876.9px** | 弹性链 `.dw-main`→`.screen-reader`→`.reader-body`→`.mobile-reader` 上默认 `min-width: auto`（=不许缩到内容最小宽度以下），一环不缩、下面全按"内容想多宽"排；再被 `.dw-layout` 的 `overflow: hidden` 默默裁掉 |
| ② | **库页论文卡片右侧被裁** | 网格轨道 = **573.3px**（可用 284px）、卡片被裁 **265px** | 卡片名带上传落盘的存储前缀（32 位 hex + `_` + 原名），**整串没有可断点** → 卡片 min-content = 465.9px → 网格轨道被顶宽。`grid-template-columns: 1fr` 在手机档是**生效的**（实测列数确实是 1），但轨道宽度由 min-content 决定 |
| ③ | **处理过程「文献」下拉超出屏幕被裁** | `label.proc-field` = **464px**、`select` = **443.5px**（右边界 534） | 下拉里最长的选项名（带哈希前缀的文件名）撑宽 `<select>`，`<select>` 再撑宽外层 `label`；`max-width: 100%` 原来**只写在下拉上**，而它先要有个边界，百分比才谈得上 |
| ④ | **「我的」会话表 661px 塞在 234px 里** | `thead` 超 **386.5px** | **不是 bug**：`.me-table { display: block; max-width: 100%; overflow-x: auto }` 已就位，表格**自己横滚**（`scrollWidth` 661 > `clientWidth` 234，可滚）。这张表列多，横滚是设计选择 |

### 顺带量到的（都在**已知限额内**，没有当场改）

- **目录层级缩进是生效的**：一级 `left=73`、二级 `left=83`，来源是父 `li` 的 `padding-left`
  （`calc(var(--toc-depth) * 10px)` 在 <720 档）。⚠️ 量的时候要量**父 `li`**——
  量子元素 `.toc-item` 的 `padding-left` 会把它的行内留白当层级，得出"缩进没生效"的错误结论。
- **底部标签栏没有盖住任何真内容**：`has-tabbar` 生效、`--tabbar-h: 56px`、标签栏本体 45px 高贴底、
  `.dw-main` 的 `padding-bottom: 56px` 到位。探针在阅读页报的 3 条"跨过标签栏顶边"的文字，
  全部落在**助手抽屉自己的滚动区里**（`top: 779` 那类）——它们本来就该被滚过去，不是被压住。
- **起草页在 390 是单栏且不溢出**：`.wr-materials` / `.wr-helper` 都是 `display: none`，
  `.wr-editor` 是 `<textarea>` 323px、`overflow-wrap: break-word`、横滚 0；
  编辑框与「改前／改后」两栏 diff 各 273px，都装得下。
- **`/memory` 页仍是「记忆页还没做」的诚实提示**（形态 v2 的分期任务，本轮未动）。

## 三、修了哪三条（修复后逐条复量）

修复都在 `frontend/src/style.css`，每条只加最少的那一两条声明（没有重排任何既有段落）：

| # | 改法 | 量测对照（390 视口） |
|---|---|---|
| ① | `.dw .mobile-reader` 加 `min-width: 0` | `.mobile-reader` **904.9 → 332**；目录 **876.9 → 295.3**；阅读页"被裁元素" **596 → 0** |
| ② | `.dw .paper-card .fname` 加 `overflow-wrap: anywhere` | 网格轨道 **573.3 → 284**；库页"被裁元素" **31 → 0** |
| ③ | 手机档（<720）里 `.proc-field` 加 `max-width: 100%`；`.proc-select` 加 `max-width: 100%` + `flex: 1 1 auto` + `min-width: 0` | `.proc-field` **464.5 → 299.3**、下拉 **444 → 275.9**（右边界 378 < 390）；处理过程"被裁元素" **5 → 0** |

- ⚠️ **②的坑**：病根是"最小内容宽度"，所以 `min-width: 0` / `overflow: hidden` **都治不了**
  （实测：加了格子仍是 573.3px）——只有**能断行**的那条 `overflow-wrap: anywhere` 有效。
- ⚠️ **③的坑**：`max-width: 100%` 只写在下拉上时 `label` **仍是 464px**（百分比要以父级为界）；
  两条都写之后还**差 8.5px**（`max-width: 100%` 按 `label` 的内容盒算，还要加 `gap` 与「文献」两字），
  所以下拉还要能参与收缩（`flex: 1 1 auto` + `min-width: 0`）才正好落进栏里。
- **守卫**：`frontend/tests/narrow-overflow.test.js`（8 条）。⚠️ happy-dom **不会真应用外部样式表**，
  所以守的是**规则位置**：顶层档规则的花括号深度必须是 0（少一个 `}` 会整段掉进上一个 `@media`，
  桌面档静默失效）；手机档规则必须**恰好**在 `@media (max-width: 719px)` 里。
  每条守卫都带一句"这条量出来的数字是多少"，免得以后被人当冗余删掉。
- **基线**：前端 **409 passed**（+8）、构建通过；后端 `ruff check .` 干净、**pytest 388 passed**
  （另 28 个 error 是本机受限沙盒写不了临时目录的 `PermissionError`，与代码无关）。
