# Agent 工具箱清单与设计规则（2026-10-18）

> 这份文档回答一个问题：**这个 agent 到底能用什么**。
> 工具的权威定义在代码（`backend/app/agent/packs/*.py`），
> 这里的表格由 `GET /api/agent/scenes` 的 `tools` 字段**实时可核对**——
> 文档说有多少个，接口就该吐出多少个。

## 一、为什么要这份清单

第一版只把「检索知识库」包成了工具，等于**把 agent 当成了搜索引擎**。
这个项目真实的能力面远不止检索：翻译任务、导读与术语表、素材卡、草稿、引文、
参考文献排版、校对检查、记忆与偏好。

清单的作用是把"能力面 → 工具 → 场景"这条链固定下来，
避免**拍了脑袋加工具**，也避免**明明有能力却没给 agent**。

## 二·五、挂载结果（实测，2026-10-18）

```
read_ask      → 14 个工具
  search_library, read_blocks, search_terms, list_tasks, get_understanding,
  get_progress, request_retranslate, get_preferences, search_memories,
  list_sections, read_section, compare_documents, list_figures, read_figure

write_compose → 14 个工具
  list_drafts, read_draft, search_library, read_blocks, search_terms,
  list_citations, suggest_citation, run_check, format_bibliography,
  list_materials, get_material, create_material,
  save_memory, save_term_preference
```

**两个场景都是 14 个工具**，都在 15 以内 → **本轮不拆场景**
（拆了反而让用户在"该找哪个助手"上多一次选择）。
超过 15 就该拆，理由：模型选工具的准确率会随工具数上升而下降。

✅ **重复已合并（2026-10-18）**：`writing.search_materials` 退役，
素材检索统一走 `materials.list_materials`（它还会过滤软删、标"源文献已删除"、转义通配符）。
同一个能力留两个工具名，模型会随机挑一个，行为还不一致——比缺工具更糟。
用例 `test_materials_search_lives_in_one_place` 同时守住"能搜"和"旧工具已退役"。


## 二·六、写作侧：AI **可以直接写正文**（2026-10-19 取消"不代写"红线）

用户明确要求："可以代写，本质上它是要改的"。所以口径从
「只给建议」改成 **「可以直接落笔，用户可以再改」**。

两条通道，各有用途：

| 通道 | 谁决定落地 | 适用 |
|---|---|---|
| `ops`（append / prepend / replace / insert_after） | **自动**写进正文，给一次整批撤销（20 秒） | 写一节、重写一段、补结论、按模板搭骨架 |
| `revisions`（original → revised） | 用户点「采用」才落地，可逐条/批量 | 只想改一句、想先看对比 |

安全网（不是诚信，是别把稿子写坏）：

1. 需要锚点的操作（`replace` / `insert_after`），`anchor` 必须**逐字**来自稿子，
   服务端 `verify_writes` 逐字核对（换行归一后比对），对不上就丢掉；
2. 空文本、未知 mode 一律丢；
3. 写入后正文标 `dirty`（**不偷偷存库**），并由前端给 20 秒整批撤销。

> 已实测（真模型）：正文 105 字 → 413 字自动写入，提示「AI 已写进正文（1 处）· 撤销」，
> 点撤销后**精确回到** 413 字。

## 二·七、这批在并行开发的四件（目标：让"写作"能交稿）

| 能力 | 解决哪个槽点 | 落点 |
|---|---|---|
| 期刊模板**可填**（骨架写进正文） | "选了模板只给我一行字" | `frontend/src/writeTemplates.js` + 写作页 |
| 稿子导出 **.md / .docx** | "没有 Word 就等于没有交稿" | `routers/draft_export.py`（docx 走引擎 venv，不破后端 6 依赖红线） |
| **综述矩阵**（文献×方法×结论×可引用句） | "写综述全靠手工抄表" | `packs/matrix.py`（工具）+ 后续界面 |
| **版本历史**（AI 改稿能回滚） | "AI 一写我就不知道原来什么样了" | `DraftVersion` + `/versions` 端点 |


### 部署前提：Word 导出要在**引擎环境**装 python-docx

`.docx` 的生成跑在引擎 venv 的子进程里（后端仍只有 6 个依赖）。
没装时接口回 **503 + 人话**（「Word 导出需要引擎环境……」），前端把这句话原样提示——
**不会**给出半成品文件。

```powershell
# 只需一次；路径取 backend/.env 里的 DOCWISE_ENGINE_PYTHON
& "<引擎 venv>\Scripts\python.exe" -m pip install python-docx
```

实测（2026-10-19）：未装 → 503 人话；装后 → 200、`未命名草稿.docx` 36 KB，
字体/标题层级/参考文献列表都按 Markdown 结构映射。


## 二·八、Skill 层：板块专属知识（2026-10-19）

工具是"手"，Skill 是"手艺"。两层分开的理由：把体例规则、排版规范写进 prompt 会撑爆上下文，
写进工具又不合适（它不是动作）。

| 层 | 是什么 | 形态 |
|---|---|---|
| Tool / Pack | 可执行函数 | `app/agent/packs/*.py` |
| **Skill** | **知识 + 流程 + 判据** | `app/agent/skill_docs/<name>/SKILL.md` + `_index.json` |
| MCP | 接外部系统（Zotero/Overleaf） | 不在本期 |

三条规则：

1. **渐进披露**：prompt 里只放索引（每条 ≤40 字，实测写作板块 3 个技能索引共 151 字），
   模型判断要用时调 `use_skill(name)` 取正文；
2. **预算封顶**：单篇 `SKILL.md` 读取上限 4000 字（超出截断并标注）；
   「一轮最多 2 个」是 prompt 规则（工具层拿不到轮次计数）；
3. **按板块隔离**：`applies_to` 决定谁能取——写作板块取不到「怎么精读」的 skill。

当前预装（写作）：`journal-format`（体例）、`typesetting-rules`（排版）、`revision-protocol`（改稿）。
读懂板块的技能在 P3 补（`close-reading` / `quote-grounding` / `term-consistency` / `cross-doc-matrix`）。

## 三、场景挂载原则

| 场景 | 该挂哪些包 | 理由 |
|---|---|---|
| `read_ask`（读懂） | `library` `terms` `tasks`（+ `translate`） | 读懂侧要能"找到那篇 → 读段 → 对术语 → 看进度" |
| `write_compose`（写作） | `writing` `library` `terms` `cite`（+ `check` `biblio` `memory` `materials`） | 写作要"读稿 → 找依据 → 统一术语 → 查引文 → 排版 → 自查" |

**一个包可以被多个场景共用**（`library`、`terms`），这是刻意的：
能力复用，权限（谁能用）由场景白名单决定，不靠复制代码。

## 四、四条硬规则（写工具前先对照）

1. **读工具随便给，写工具必须显式确认**
   写操作（重译、建素材、插引文、改稿）的入参必须有 `confirm`，
   缺省状态只解释"需要用户在界面上确认"，不真做。
   理由：agent 不能被一句话就改坏用户的东西。

2. **归属过滤必须在工具里做**
   `ctx.user_id` 不匹配一律当"找不到"，不靠前端拦。
   已有用例钉着这条（读别人的草稿/文献/素材都要读不到）。

3. **不许 import `pydantic_ai`**
   `packs/` 与 `scenes/` 只认 `contracts.py` 的 ABI；换引擎只改 `runtime.py`。
   有结构用例正则匹配真实 import 语句。

4. **handler 签名固定 `(ctx, args: dict | None = None)`**
   runtime 以 `spec.handler(ctx, payload_dict)` 调用。
   写成 `(ctx, draft_id=None)` 的后果实测过：整个 payload 被当成 draft_id →
   `int(dict)` 抛异常 → 模型重试两次后整轮失败（`Tool ... exceeded max retries`）。

## 五、还没包的能力（按价值排序）

✅ **已完成**（2026-10-18 第二批）：
- **长文精读** → `outline.list_sections` + `outline.read_section`（先看结构、只读一节）；
- **对比阅读** → `compare.compare_documents`（导读逐字段 + 术语交并差）；
- **写作改写支持整段** → `revisions.original` 可以是一整段多句（服务端校验时**归一换行**，
  否则草稿的 `\r\n` 与模型的 `\n` 会让"逐字比对"假失败）；
- **前端**：批量采用 / 忽略 / 撤销 / 复制改后文本 / 长建议折叠。

还在等：
1. **插图与表格**：`list_figures` / `read_figure`（块分级的 caption 判据可直接用）—— 并行开发中；
2. **记忆写入**：`save_memory` / `save_term_preference`（带 `confirm`，不动 `hits`）—— 并行开发中；
3. **任务生命周期**：`retry` / `cancel` / `purge`（写操作，全部要 confirm）；
4. **摘要**：`summarize(task_id)`（要调模型，属于"工具里再调模型"，成本要单独评估）。
