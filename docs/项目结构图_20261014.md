## 0. 怎么重新生成（三条命令，工具已装好）

用的是 **[colbymchenry/codegraph](https://github.com/colbymchenry/codegraph)**（**MIT**，73k★，**100% 本地、不上传代码**、索引是 SQLite）。
本机已装（`codegraph --version` → `1.4.1`），索引目录 `.codegraph/` **已在 `.gitignore` 里**（生成物，不进仓库）。

```bash
# ① 建/重建索引（新克隆一台机器跑一次；之后它自动跟随文件变化）
codegraph init

# ② 看规模与构成
codegraph status

# ③ 查"改这个会影响谁" —— 最有用的一条
codegraph impact traceTo          # 换成任何函数/方法名

# ④ 问一个流程问题（返回相关符号的**逐行源码 + 调用路径 + 波及面 + 有无测试**）
codegraph explore "上传一篇文献之后，worker 是怎么一步步处理的"
```

⚠️ **`codegraph` 不是项目依赖**：它对我们的运行时**零影响**（不进 6 个后端依赖、不进 `package.json`）。
**它只是开发期的一面镜子**：换台机器不装它，项目照样跑。

**`App.vue` 为什么停在 464 行**（不是没搬干净，是结构性的）：
`syncFromRoute`（路由分发）要调 `openTask`（`useReader`），而 `openTask` 又要写 `view` 并写地址（外壳）——
**互为因果**，把路由接线搬进任何 store 都会绕成环。要再降只能把「账号会话」也下放，见 issue #86 里那两条去路。
⚠️ **判据「`App.vue` < 200 行」已由用户 2026-10-14 明确挂起**，别自己捡起来做。

**store 依赖方向（硬约束：`stores/` 之间没有任何环）**：

```
useUi ──┐（叶子）
useTasks ┴（叶子）
useAsk ───→ useUi
useReader ─→ useUi · useAsk · useTasks
useLibrary→ useReader
useWrite ─→ useReader · useTasks · useUi     ← 起草页（#/write）：跳回原文复用 useReader.traceTo
App ─────→ 全部
```

外壳才有的能力（当前屏 `view` / 写地址 / 刷新列表）由 `App.vue` 用 `initReader()` / `initLibrary()` / `initAsk()` **注入**——
**store 不 import `App.vue`**（那就绕成环了）。

## 附：本文的数字怎么来的

```bash
git ls-files | wc -l                    # 受控文件总数
codegraph status                        # 索引规模、节点构成、语言分布
codegraph files --max-depth 3           # 目录树
codegraph impact <符号名>               # 改动波及面
codegraph explore "<流程问题>"           # 流程 + 逐行源码 + 有无测试
```

⚠️ **PowerShell 下的三个坑（都真踩过，第二次刷新时又踩了一遍）**：

```powershell
# ① 数行数：Get-Content | Measure-Object -Line 会【跳过空行】，App.vue 少 90 多行
([IO.File]::ReadAllText($p) -split "`n").Count - 1     # ← 用这个

# ② 列受控文件：git ls-files 对中文名会转义（docs/\344...），按普通输出拼路径会【静默跳过】
$files = @(git ls-files -z) -join '' -split "`0" | Where-Object { $_ }   # ← 必须带 -z

# ③ codegraph 的数字要【先 sync 再读】：索引旧了会报出偏小的规模，
#    而它不会提醒你"这是上一次的"（第二次刷新时就先读到了旧的 88 文件）
codegraph sync; codegraph status
```

> ⚠️ **改完代码请重跑 `codegraph sync`**（通常自动同步），并在**动过结构**时回来更新本文第 2 / 3 节。
> 如果发现本文与命令输出不一致 —— **以命令输出为准**，然后**把本文改对**。
