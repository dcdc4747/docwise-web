# docwise-web 组员入门指南

欢迎加入！这份文档是给新组员的**上手路线**，按"由浅入深"排好了 4 步。看完并动手做完，你就能看懂这个项目、装上工具、跑起来，并且知道怎么跟团队协作。

> **先看三句话，知道我们在做什么**

- 这是一个**文档翻译智能体**：上传英文文献 PDF，拿到"像原文档的中文版"（纯中文 / 中英对照）。
- 核心理念：**Agent 是大脑，程序是手脚**——AI 负责决策（定流程、查质量、决定返工），程序负责精确执行（取字、排版）。
- 技术栈：前端 **Vue3 + Naive UI**，后端 **Python + FastAPI**，数据库 **SQLite**（将来可换 PostgreSQL）。

## 第 1 步：先搞懂"这个项目到底长什么样"

开始看代码之前，先建立全局认知。这一步不写代码，纯科普，半小时就能看完。

### 1.1 什么是前后端分离？

一句话：**前端是"接待柜台"，后端是"翻译车间"。**

- **前端（Vue）**：负责给用户看的界面。上传 PDF、显示进度、预览、下载，都是它的活。
- **后端（Python）**：负责真正"干活"。把 PDF 抽字、翻译、排版、出稿，处理文档、存数据。
- 两者通过 **API 接口**通信：前端把"用户想要什么"翻译成请求发给后端，后端把结果或进度返回给前端。

### 1.2 为什么这个项目必须前后端分离？

**不是为了显得高级，而是被项目的技术性质逼出来的最优解。** 4 个原因：

**① 技术栈根本不一样，只能分开。**
处理文档的深度依赖（PDF 解析、OCR、版面识别、图处理）都**只能跑在 Python 里**，浏览器做不了；而漂亮的界面、响应式适配电脑+手机，用 **Vue** 来做最合适。两种语言/生态无法硬塞在一起，只能拆成两个服务。

**② 这是"长任务"，前端不能傻等。**
翻译一篇论文不是秒出——快档几十秒，精档要十几分钟。如果前后端不分离，前端就得一直卡着等，把浏览器都卡死。分离之后是：
```
用户上传 → 后端立刻建任务（返回 task id）→ 后台异步翻译
用户点击后 → 前端轮询 / WebSocket 实时收进度 → 显示"翻译中…30%"
跑完 → 前端拿到结果 → 预览 / 下载
```
所以这个项目才有**任务状态机 + 后台 worker + 实时进度推送（SSE）+ 轮询兜底**。这套东西天然就是前后端分离的形态。

**③ 多个人能并行干活，互不卡。**
一个人做界面、一个人做后端引擎，可以**同时开工、互不阻塞**，最后靠一套约定的 API 接口对接起来。揉成一个单体的话，改界面的人会跟改后端的人互相踩踏。

**④ 以后的东西能只换半边，不用重来。**
后面要加术语库、质检打回、OCR、Word 输出……前后端分离后，加一个通道只改后端、前端不动；换数据库只改后端、前端不动。**两边约定好接口不变，改动永远是局部的。**

### 1.3 这个项目的目录长什么样

```text
docwise-web/
├── backend/    # 后端（Python + FastAPI）
│   └── app/
│       ├── main.py      # 接口入口：/api/health、/api/tasks、新建任务、SSE 进度
│       ├── models.py    # 数据库表：任务卡、任务历史、每块状态
│       ├── worker.py    # 后台 worker：按任务找引擎翻译、推进度
│       └── engine/      # 翻译引擎（可插拔，按档位选）
├── frontend/   # 前端（Vue3 + Naive UI + Vite）
└── docs/       # 文档（你正在看的这份）
```

> ✅ **第一步学完，你能做到**：画出"前端 ↔ 后端 ↔ 数据库"的架构草图，说清一条 PDF 从上传到出稿大概经过哪些环节。

## 第 2 步：Git + GitHub 协作（**重中之重**）

这个项目是**多人在同一个仓库协作**，靠 Git 和 Pull Request（PR）管理代码。这步不扎实，后面全卡住。**光看视频没用，一定要动手做一遍。**

### 2.1 要会这几件事

- 从仓库拉代码：`git clone`
- 建自己的分支：`git checkout -b feat/xxx`
- 改动、提交：`git add` → `git commit` → `git push`
- 把改动合进主分支：发一个 **Pull Request**
- 同步别人最新代码：`git pull`

### 2.2 这个项目的协作铁律（务必记住）

1. **开工先同步**：`git checkout main` → `git pull`。
2. **每个任务建独立分支**，命名 `feat/xxx`（功能）/ `fix/xxx`（修复）/ `docs/xxx`（文档）。**禁止直接在 main 上改代码**。
3. 提交信息格式：`feat(scope): 说明`（scope 如 frontend / backend）。
4. **一定要推 PR**：代码写在自己的分支上，然后发 Pull Request，PR 是进主分支的唯一入口。**不要只本地提交不推送。**
5. **不要直接推 main**：main 有保护，必须由仓库管理员审批后才能合并。
6. 合并统一用 **Squash and merge**（由负责人操作），合并后删掉分支。
7. 遇到冲突：`git pull origin main` 到自己分支，解决冲突后 add + commit + push。

## 第 4 步：读懂本项目的一条核心链路

重走第 1 步的认知，然后直接用 AI 帮你逐段看代码，把"一次翻译任务"从头到尾串起来：

```
用户上传 PDF
   → 前端把这个文件发给后端（POST /api/tasks，建任务，立即返回任务ID）
   → 后端后台 worker 接手：读 PDF → 抽文字 → 调翻译引擎 → 排版 → 出稿
   → 前端实时收进度（SSE/轮询）
   → 翻译完成 → 前端预览 / 下载
   → 数据库里记下这次任务（历史记录）
```

> ✅ **第四步学完，你能做到**：知道一个翻译任务从上传到出稿经过了哪些模块、每块状态是什么、遇到问题该去哪个文件里找。
